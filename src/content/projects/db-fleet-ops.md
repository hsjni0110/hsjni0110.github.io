## 백업 파일의 복원·테이블 조회 자동화

DB FleetOps에서는 백업 파일을 임시 DB에 복원하고 필요한 테이블을 조회해 결과를 기록하는 기능을 구현했습니다. 복원 검증에 성공했더라도 임시 DB 정리가 실패한 경우는 별도로 표시했습니다.

데이터를 안전하게 관리하고 장애 이후 복구하는 방법, 반복적인 DB 관리 작업의 자동화를 학습하려고 시작한 프로젝트입니다. AI와 시장·운영 사례를 조사하며 문제 상황을 가정했으며, 실제 고객에게 운영 요구를 받은 도구는 아닙니다.

## 전체 일치 검증보다 복원 가능성 확인 우선

백업은 장애가 발생했을 때 데이터를 복구하기 위한 수단이라고 생각했습니다. 파일이 만들어졌다는 사실만으로는 복구할 수 있는지 알 수 없기 때문에, 실제로 복원하고 필요한 테이블을 읽을 수 있는지를 확인하는 기준을 잡았습니다.

처음부터 원본과 복원본 전체의 데이터 일치까지 검증하면 비용과 복잡도가 커진다고 봤습니다. 먼저 임시 DB 복원과 필수 테이블 확인을 연결하고, 이후 검증 수준을 높이는 순서로 구현 범위를 정했습니다. 따라서 현재의 성공 기준은 전체 데이터의 동일성이 아니라 복원과 테이블 조회 가능성입니다.

## 복원·정리 상태 분리와 DB 기반 작업 관리

백업 복원, 테이블 확인, 결과 기록을 순서대로 연결했습니다. 임시 DB가 계속 남으면 저장 공간을 차지하고 운영에 영향을 줄 수 있어, 복원 검증의 성공과 정리 실패를 같은 결과로 묶지 않았습니다. 운영자가 정리 실패를 알고 후속 조치를 할 수 있도록 별도 상태로 기록했습니다.

비동기 작업은 별도 큐 대신 기존 DB에서 상태와 결과를 관리했습니다. 비동기 처리가 필요하다는 이유만으로 Kafka까지 도입할 필요는 없다고 판단했습니다. 학습 프로젝트라 요청이 많지 않을 것으로 예상했고, 우선 기존 DB로 단순하게 시작하는 편이 운영 부담을 줄일 수 있다고 봤습니다. 이 규모 판단은 부하 측정 결과가 아닌 초기 가정입니다.

## 테이블 누락·정리 실패의 단위 테스트

필수 테이블의 존재·누락, 복원된 테이블이 없는 경우, 선택적인 행 수 조회, 정리 실패를 다루는 단위 테스트를 작성했습니다. 각 상황에서 어떤 결과를 남기는지와 처리 순서를 확인하는 검사이며, DB 응답과 명령 실행에는 대체 객체를 사용했습니다.

이 테스트가 실제 운영 환경의 손상된 백업을 복원해 검증했다는 뜻은 아닙니다. 실제 DB·백업 파일을 대상으로 한 복원 검증과 대용량 부하 검증은 구분해야 합니다.

## 복원 실패 후 정리 보장과 데이터 일치 검증 과제

원본·복원본 전체 데이터의 일치와 대용량 복원 비용은 아직 검증하지 않았습니다. 현재 상위 처리 흐름에는 복원에 실패한 뒤 임시 DB 정리가 항상 실행되지 않는 경로도 남아 있습니다. 정리 실패를 별도로 기록하는 기능과, 모든 실패 경로에서 정리를 시도하는 보장은 다른 문제입니다.

다음 단계에서는 실패 경로의 정리 처리를 보완하고 데이터 검증 범위를 높여야 합니다. 별도 큐 도입은 요청이 실제로 늘어나 병목이나 운영 한계가 확인됐을 때 검토할 계획입니다.
