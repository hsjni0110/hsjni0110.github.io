## 맥락

데이터를 안전하게 관리하고 장애가 발생했을 때 복구하는 일, 반복 관리 작업의 자동화에 관심이 있어 시작했습니다. AI와 함께 시장과 운영 사례를 조사하며 학습할 문제 상황을 가정했습니다.

실제 고객의 운영 요구를 받아 만든 도구는 아닙니다.

## 판단

백업은 장애가 났을 때 데이터를 복구하기 위한 것입니다. 파일이 생성됐다는 사실만으로 그 목적을 달성했다고 볼 수 없어, 실제 복원 여부까지 확인하도록 했습니다.

처음부터 모든 데이터의 일치까지 검증하는 것은 비용과 복잡도가 크다고 보았습니다. 먼저 임시 DB에 복원하고 필요한 테이블을 확인하는 핵심 흐름을 완성한 뒤 검증 수준을 높이기로 했습니다.

## 실행

복원과 테이블 확인, 결과 기록을 연결했습니다. 임시 DB가 남으면 저장 공간과 운영에 영향을 줄 수 있으므로, 검증이 성공해도 정리가 실패하면 별도 상태로 운영자가 알 수 있게 했습니다.

비동기 작업 관리에는 별도 큐 대신 기존 DB를 선택했습니다. 학습 프로젝트라 요청이 많지 않을 것으로 예상했고, 우선 작업 상태와 결과를 한곳에서 관리하는 편이 단순하다고 판단했습니다.

## 확인

테스트에는 필요한 테이블 존재·누락, 복원된 테이블 없음, 선택적인 행 수 조회와 정리 실패 등의 상황을 다루는 검사가 있습니다. 관련 단위 테스트는 DB 응답과 명령 실행을 대체 객체로 구성합니다.

이 검사는 판정과 흐름의 근거이며, 실제 손상된 백업을 운영 환경에서 복원해 검증했다는 뜻은 아닙니다. DB 기반 처리가 충분하다는 판단도 부하 측정 결과가 아닌 시작 단계의 가정입니다.

## 한계와 다음 단계

전체 원본·복원본의 데이터 일치와 대용량 복원 비용은 검증 범위 밖입니다. 확인한 상위 처리 코드에서는 복원 실패 후 정리가 항상 수행되는 것은 아니므로, 모든 실패에서 정리를 보장한다고 말할 수 없습니다.

실제 병목과 한계를 확인하면 별도 큐 도입을 검토하고, 복원 검증 범위를 높이는 순서로 발전시킬 수 있습니다.
