## 맥락

소설을 스크립트와 음성으로 옮길 때, 중요한 것은 각 문장을 생성하는 일만이 아니었습니다. 듣는 사람이 같은 인물을 같은 인물로 따라갈 수 있어야 했습니다.

긴 원문을 나눠 처리하더라도 이름과 호칭이 달라졌다는 이유로 인물이 나뉘면 안 됩니다. 같은 인물의 목소리가 바뀌거나 대사가 다른 인물에게 연결되면 청자가 혼란스러워질 수 있다고 예상했습니다.

## 판단

처음에는 이전 등장인물 정보를 다음 생성에 전달하고, 이름·설명과 인물 ID를 구분해 일관성을 유지하려 했습니다. 하지만 실제 음성을 듣고 팀원들과 확인하는 과정에서 발화자 매핑 오류와 LLM 결과의 불확실성이 남아 있었습니다.

팀과 함께, 모델의 정확도를 높이는 것만으로 해결하기에는 한계가 있다고 판단했습니다. 생성 결과를 작가가 직접 확인하고 수정할 수 있는 흐름을 마련하기로 했습니다.

> 자동 생성으로 초안을 만들고, 작가가 결과를 바로잡을 수 있게 했습니다.

## 실행

저는 스크립트 생성, 등장인물 동기화, 음성 생성 흐름을 주로 맡았습니다. 인물 ID와 이전 문맥을 활용한 연결, 대사 수정 API, 등장인물 이름과 목소리 선택 기능을 구현했습니다.

검토 기능을 넣은 뒤에는 수정 자체의 번거로움도 살폈습니다. 잘못 연결된 대사를 찾아 고치는 일을 돕기 위해 발화자마다 색을 달리하는 개선안을 제안하고 화면을 구현했습니다. 여러 문장을 수정할 수 있는 API도 맡았습니다.

작가 검토 단계를 도입한 것은 팀의 공동 결정이고, 색 구분 개선안과 해당 화면·API 구현은 제가 담당한 부분입니다.

## 확인

생성된 음성을 직접 듣고 팀원들과 함께 사용하며 결과를 확인했습니다. 색으로 발화자를 구분하니 잘못 매핑된 대사를 찾고 수정하기 편해졌다는 반응이 있었습니다.

이는 **팀 내부 사용의 정성적 피드백**입니다. 실제 작가 대상 사용성 시험이나 수정 시간의 정량 측정은 하지 않았습니다.

현재 공개 코드에는 발화자별 색 구분과 문장별 편집, 복수 수정 요청을 받는 API가 남아 있습니다. 당시 여러 문장 선택 화면의 캡처는 확보하지 못해, 해당 UI를 재구성한 이미지는 싣지 않았습니다.

## 한계와 다음 단계

LLM이 인물을 생략하거나 잘못 연결할 가능성은 남아 있습니다. 인물 일관성을 자동으로 검증하는 전용 테스트의 근거도 확보하지 못했습니다.

사람이 수정할 수 있게 만드는 데서 끝내지 않고, 어떤 부분을 검토해야 하는지 더 쉽게 알아볼 수 있어야 합니다. 이 경험을 통해 자동화의 정확도와 오류를 바로잡는 사용자 흐름을 함께 설계하는 일이 중요하다는 것을 배웠습니다.
