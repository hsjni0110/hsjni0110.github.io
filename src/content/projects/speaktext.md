## 원문 분할 처리에서 예상한 인물 연결 오류

SpeakText에서는 소설을 스크립트와 음성으로 옮기는 기능을 개발했습니다. 저는 스크립트 생성, 등장인물 동기화, 음성 생성을 주로 맡았고, 이후 작가의 검토를 돕는 편집 화면과 API도 구현했습니다.

구현 전부터 긴 원문을 나눠 처리할 때의 인물 연결을 고민했습니다. 같은 인물을 서로 다른 이름이나 호칭으로 표현했다고 해서 별개의 인물로 생성하면, 중간에 목소리가 바뀌거나 대사가 다른 사람에게 연결될 수 있기 때문입니다. 문장 하나의 생성 결과뿐 아니라, 청자가 이야기 전체에서 같은 인물을 일관되게 따라갈 수 있는지가 중요하다고 봤습니다.

## LLM 보완과 작가의 직접 수정 기능 도입

인물의 일관성을 유지하기 위해 이전 등장인물 정보를 다음 생성에 전달하고, 이름·설명과 인물 ID를 구분해 연결했습니다. 하지만 팀원들과 생성된 음성을 직접 듣는 과정에서 발화자가 잘못 연결되는 오류를 확인했습니다. 이전 정보를 제공하더라도 LLM의 결과가 항상 정확하지는 않았습니다.

팀은 모델의 정확도를 높이는 것만으로 모든 오류를 해결하기는 어렵다고 판단했습니다. 그래서 작가가 생성 결과를 확인하고, 등장인물 이름·목소리와 대사 연결을 수정하는 기능을 추가하기로 결정했습니다. 자동 생성 결과에 오류가 남더라도 사용자가 잘못된 부분을 찾아 바로잡을 수 있는 방법이 필요했습니다.

## 발화자별 색 구분 제안과 화면·API 구현

검토 기능이 생긴 뒤에는 잘못 연결된 대사를 찾고 고치는 과정이 번거롭다는 문제가 있었습니다. 저는 발화자마다 색을 달리하는 개선안을 제안했습니다. 대사를 한 줄씩 읽기 전에도 누가 말하는 구간인지 구별하면, 엉뚱한 인물에게 연결된 대사를 발견하기 쉬울 것이라고 생각했습니다.

색 구분을 적용한 화면과 여러 대사를 수정하는 일괄 수정 API를 구현했습니다. 스크립트 생성·인물 동기화·음성 생성 외에도 등장인물 이름과 목소리 선택, 대사 수정 기능을 맡았습니다.

작가 검토 단계를 도입한 것은 팀의 공동 결정입니다. 발화자별 색 구분 개선안과 해당 화면·API 구현은 제가 직접 담당했습니다.

## 팀원들과의 음성 청취·편집 기능 점검

생성된 음성을 팀원들과 듣고 편집 기능을 사용하면서 발화자 연결과 수정 과정을 확인했습니다. 색 구분을 적용한 뒤에는 잘못 연결된 대사를 찾고 한 번에 수정하기가 더 편해졌다는 반응이 있었습니다.

이는 **팀 내부 사용의 정성적 피드백**입니다. 실제 작가를 대상으로 사용성 시험을 진행하거나 수정 시간을 수치로 측정하지는 않았습니다. 공개 코드에서는 발화자별 색 구분, 문장별 편집, 복수 수정 요청을 받는 API를 확인할 수 있습니다.

## 실제 작가의 오류 탐색·수정 시간 검증 과제

수정 기능을 추가했다고 해서 생성 단계의 인물 생략·연결 오류가 사라진 것은 아닙니다. 당시에는 직접 음성을 들으며 확인했으며, 확인된 자료에는 인물 일관성을 자동으로 검증하는 전용 테스트가 없습니다.

다음으로는 실제 작가가 잘못 연결된 대사를 발견할 수 있는지, 수정에 얼마나 시간이 걸리는지 확인해야 합니다. 검토 단계가 추가된 만큼 사용자 흐름도 복잡해졌기 때문에, 오류를 바로잡는 기능의 존재뿐 아니라 그 기능을 쉽게 사용할 수 있는지도 검증할 필요가 있습니다.
