# 한석진 포트폴리오 사이트 설계

작성일: 2026-10-18 (Asia/Seoul)  
상태: 2026-10-18 사용자 검토 및 설계 확정 완료  
목적: 개발자 채용을 위한 정적 포트폴리오의 이야기, 화면, 공개 범위와 근거를 정의한다.  
범위: 설계 문서. 사이트 구현·배포와 도메인 연결은 아직 진행하지 않았다.

## 1. 목표와 독자

채용 담당자와 함께 일할 개발자가 한석진을 다음과 같은 동료로 이해하도록 한다.

> 누구의 어떤 문제인지 먼저 이해하고, 상황에 맞는 해결책을 끝까지 만드는 동료.

언어·프레임워크 목록보다 문제 인식, 판단 이유, 직접 기여, 결과와 한계를 먼저 전달한다. 기술은 그 선택을 실행한 근거로 설명한다. 독자가 짧게 훑어도 핵심을 알 수 있고, 관심 사례에서는 증거를 깊게 읽을 수 있어야 한다.

성공 기준:

- 첫 화면에서 이름, 문제 해결 관점, 대표 사례와 연락 경로가 분명하다.
- 각 사례에서 대상 사용자, 문제, 선택 이유, 직접 기여, 확인 범위를 구분할 수 있다.
- 메인은 하나의 이야기로 이어지고, 상세 페이지로 직접 진입해도 이해된다.
- 이메일과 이력서에 쉽게 접근할 수 있다.
- 실제 운영 성과, 학습 실험, 사용자 가설과 개발 중인 상태를 혼동하지 않는다.

방문자 수나 채용 전환율 등 측정되지 않은 수치를 성공 실적으로 제시하지 않는다.

## 2. 핵심 이야기

전체 흐름은 기술 구현에 관심을 두던 개발자가 회사·교육·동아리·사이드 프로젝트를 통해 누구의 어떤 문제를 풀어야 하는지 먼저 묻는 방향으로 관점을 넓혀온 과정이다. 단일 사건이 모든 변화를 만들었다고 각색하지 않는다.

대표 사례의 배치는 역량을 설명하기 위한 편집 순서이며 엄격한 시간 순서가 아니다.

| 우선순위 | 경험 | 이야기에서 맡는 역할 |
| --- | --- | --- |
| 1 | SpeakText | 자동 생성뿐 아니라 사용자가 결과를 바로잡는 과정까지 개선 |
| 2 | ForgeSync | 도메인 의미와 데이터의 한계를 이해하고 판단 범위를 설정 |
| 3 | 동시생활 앱 | 사용자에게 필요한 이유를 다시 묻고 제품 기획을 전환 |
| 실무 근거 | 모플, 스마트뉴비 | 분석·구현·검증과 협업을 실제 업무에서 수행 |
| 심화 사례 | DB FleetOps, 예약 시스템 | 완료 기준, 기술 도입 범위와 데이터 정합성에 대한 판단 |

회사·동아리·아카데미 경험은 관점이 형성된 배경으로 연결한다. 사용자를 인터뷰하거나 현장에서 검증하지 않은 경험을 실사용자 요구처럼 묘사하지 않는다.

## 4. 메인 페이지 흐름

### 4.1 첫 화면

제목: **누구의 어떤 문제인지부터 생각합니다.**

이름과 핵심 문장을 가장 크게 배치한다. 작은 프로필 사진을 곁들이고 경력·관심을 2~3문장으로 설명한다. 대표 사례 보기와 이메일 연락을 제공한다. 이력서는 탐색 메뉴 또는 연락 영역에서도 접근 가능하게 한다.

소개 문안의 기준:

> 백엔드와 데이터 파이프라인을 개발하며 기술을 구현하는 경험을 쌓았습니다. 이제는 누구에게 어떤 문제가 있는지 먼저 이해하고, 상황에 맞는 해결책을 만드는 데 집중합니다.

### 4.2 관점 소개

문장: **구현하는 방법에서, 만들어야 하는 이유로 관심을 넓혀왔습니다.**

회사 경험, 멋쟁이사자처럼 네트워킹, 제조지능화 교육과 사이드 프로젝트가 점진적 변화의 배경임을 짧게 전달한다. 긴 연대기나 기술 로고 모음은 두지 않는다.

### 4.3 SpeakText

문장: **생성의 정확도에서, 수정의 편의까지.**

인물 일관성의 필요 → 실제 청취·팀 확인에서 발견한 오류 → 작가 검토·수정 단계 → 색 구분과 편집 편의 개선 순서로 설명한다. 메인에서는 문제·판단·결과를 각각 짧게 전달하고 상세로 연결한다.

### 4.4 ForgeSync

문장: **숫자를 보여주기 전에, 그 뜻을 확인했습니다.**

정지와 기록 누락의 혼동, 센서 편차와 고장·불량의 차이를 설명한다. 대시보드와 기존 화면 개선 전후를 증거로 사용하고, 관심 구간에서 당시 상태를 조사하는 흐름으로 연결한다.

### 4.5 개발 중인 앱

제목: **캐릭터와 각자의 일을 함께하는 동시생활 앱**

문장: **시작을 돕는 앱이, 또 하나의 일이 되지 않도록.**

개인 경험 → 커뮤니티에서 관찰한 유사한 어려움 → 기존 기획의 입력·대화 부담 → 앱을 켜고 자기 일을 하는 동시생활 기획으로 전환한 과정이다. 전후 비교와 핵심 기능을 글·간단한 도식으로 전달한다. 앱 화면을 연상시키는 가짜 스크린샷도 만들지 않는다.

### 4.6 실무 경험

## 5. 상세 사례 구성

공통 순서는 요약 → 맥락 → 판단 → 실행 → 확인 → 한계와 다음 단계다.

| 항목 | 필수 내용 |
| --- | --- |
| 첫 요약 | 대상 사용자, 해결하려는 문제, 프로젝트 유형·역할, 결과 또는 현재 상태 |
| 맥락 | 불편이나 위험, 발견 과정, 실제 관찰과 가정의 구분 |
| 판단 | 고려한 대안, 선택 이유와 범위 |
| 실행 | 직접 담당한 부분, 팀 공동 결정과 동료 기여 |
| 확인 | 테스트·청취·피드백·측정 결과 및 근거 링크 |
| 한계 | 미검증 항목, 알려진 미해결 문제, 후속 검증 |

필요한 지점에서만 기술과 구조를 설명한다. 역할·기간이 불명확하면 값을 만들지 않고 확인된 수준의 연도 또는 상태만 표기한다. 모든 내부 확인 상태를 방문자에게 배지로 노출하지는 않지만, 의미가 달라지는 제한은 본문에 자연스럽게 남긴다.

## 6. 사례별 사실과 표현 기준

### 6.1 SpeakText

- 팀 프로젝트. 본인 담당은 스크립트 생성, 등장인물 동기화, 음성 생성 흐름이다.
- 인물 일관성이 깨지면 목소리와 대사 연결에 문제가 생길 수 있다고 구현 전에 예상했다.
- 실제 음성을 듣고 팀원들과 확인하며 매핑 오류와 LLM 비결정성의 한계를 확인했다.
- 작가 검토·수정 단계는 팀과 공동 결정했다. 개인 단독 기획으로 표현하지 않는다.
- 색 구분 개선안·화면·일괄 수정 API는 본인이 담당했다고 확인했다.
- 팀 내부 사용에서 잘못 매핑된 대사를 찾고 수정하기 편해졌다는 정성적 피드백이 있었다. 정량 수치·외부 작가 검증은 없다.
- GitHub에서 발화자 색 구분, 문장별 편집, 복수 업데이트를 받는 API가 확인됐다.
- 여러 문장 선택 UI는 현재 화면과 확인한 해당 파일의 과거 10개 버전에서 찾지 못했다. 사용자 진술을 부정하는 뜻은 아니며, 보존된 시각 근거가 부족한 상태다.
- 인물 일관성 전용 자동 테스트를 확인하지 못했다. 코드 읽기와 테스트 실행을 혼동하지 않는다.
- 수정 후 음성 자동 재생성·무효화, 검수 완료를 강제하는 출판 절차를 구현했다고 주장하지 않는다.

권장 표현: “팀과 함께 작가가 검토·수정할 수 있는 흐름을 마련하고, 발화자 색 구분과 편집 기능으로 수정의 번거로움을 줄이려 했습니다.”

### 6.2 ForgeSync

- 개인 학습 프로젝트. 기획·데이터 설계·백엔드·프런트엔드·검증을 맡고 AI 코딩 에이전트를 활용했다.
- 아카데미와 자료 조사로 정지·가공 시간 변화 구간을 조사하는 엔지니어를 가정했다. 실제 현장 요구를 청취한 프로젝트가 아니다.
- NIST 공개 설비 1대의 하루 기록을 활용했다. 기존 포트폴리오는 원본 115,991줄을 명시한다.
- 작은 IQR에서 점수가 과장되고 다수 지표의 최댓값이 전체 등급을 좌우하는 문제를 검토했다.
- 현재 정책은 가공 시간을 주 판정 기준으로 두고 센서 편차는 참고 정보로 제공한다. 10% 기준을 실증된 현장 정상 범위로 제시하지 않는다.
- 코드 설명의 “94개 중 92개”는 센서 채널이 최상위 근거였던 구간 수를 뜻한다. 초기 자기소개서의 요약과 혼용해 불량·오탐 건수로 쓰지 않는다.
- 실제 품질 정답이 없으므로 불량 탐지 정확도 향상이나 오탐률 감소를 주장하지 않는다.
- 기록 없음과 정지를 구분하고, 알람의 동시 발생을 원인으로 단정하지 않는다.
- 공개 PDF의 시험 결과는 해당 기록·조건의 결과다. 현재 소스를 직접 재실행한 결과로 표현하지 않는다. 기존 PDF의 미해결 결함은 수정 여부를 새로 확인하기 전까지 해결됐다고 쓰지 않는다.

권장 표현: “정답 데이터가 없는 상황에서 해석 가능한 범위를 정하고, 가공 시간과 센서 관측의 역할을 나눴습니다.”

### 6.3 동시생활 앱

- 개인 경험과 커뮤니티 조사에서 시작했다. 혼자 할 일을 시작하고 지속하기 어려운 상황이 문제 가설이다.
- 커뮤니티에서 함께 공부하는 영상·온라인 공간 사용 사례를 관찰했다. 체계적 수요 조사나 시장성 검증으로 확대하지 않는다.
- 실제 사람과의 시간 조율·관계 부담, 영상에서 관계가 쌓이지 않는 점을 대안 선택의 근거로 생각했다.
- AI 일정 친구 → 자기관리 AI 일정 친구 → 자기 일상을 사는 캐릭터와 각자의 일을 하는 경험으로 기획을 전환했다.
- 기존 버전의 테스터를 모집해 오픈 톡방 피드백을 받았다. 새 버전은 개발 중이며 사용자 검증 전이다.
- 일정 입력·AI 대화 부담을 줄이는 것이 의도다. 새 버전의 사용성·지속성 개선이 입증됐다고 표현하지 않는다.

- 문제는 매일 증분되는 데이터의 배치 처리 시간이 길다는 것이었다.
- 병목 분석, SQL 실행 계획 확인, 개선안 검토, Custom Incremental 구현, 처리 시간·건수·업무 규칙 확인을 모두 직접 수행했다고 사용자가 확인했다.
- Citus 중앙 노드 부하 집중과 불필요한 데이터 이동, dbt 기본 증분 적재 흐름을 분석했다.
- 구체적인 처리 시간 단축 수치는 확인되지 않았다.
- 후속 고객 업무·수요예측·재고 배분에 미친 영향은 사용자가 정확히 기억하지 못하므로 주장하지 않는다.
- 직접 담당과 “아무 도움 없이 혼자 했다”는 다른 주장이다. 후자는 사용하지 않는다.

- 멋쟁이사자처럼: 2024년 교육생, 2025년 운영진. 백엔드 운영진 표현은 이력서에 근거한다.

- 충남대학교 컴퓨터융합학부 2020.03 - 2026.02, HINT 제조지능화 과정 2026.07 - 현재는 문서 근거다. 수료 상태는 공개 시점에 다시 확인한다.

### 6.6 심화 사례

DB FleetOps:

- DBMS 관리 관심에서 시작한 학습 프로젝트다.
- 백업의 복구 목적 때문에 실제 복원·필요 테이블 확인을 성공 기준에 포함했다.
- 전체 데이터 일치 검증은 비용·복잡도를 고려해 후속 범위로 두었다.
- 정리 실패를 운영자가 알 수 있도록 별도 상태로 드러냈다.
- 적은 요청을 예상하는 학습 환경에서 DB로 단순하게 시작했다. 부하 측정으로 별도 큐가 불필요하다고 입증한 것은 아니다.
- 분석한 복원 단위 테스트는 DB·명령 대체 객체를 활용했다. 실제 손상 백업 복원 시험과 구분한다.
- 확인 당시 상위 처리 경로에서 복원 실패 후 항상 정리되는 것은 아니므로 “모든 실패에 정리 보장”이라고 쓰지 않는다.

예약 시스템:

- 동시성·트랜잭션을 학습하기 위해 예약 도메인을 선택했다.
- 결제 중 사용자의 좌석을 보호하고, 이탈한 사용자 점유를 회수하려 했다.
- 5분은 검증된 최적값이 아닌 학습용 정책이다.
- 결제 이벤트 지연과 만료의 충돌은 당시 고려하지 못한 현재 한계로 사용자가 확인했다.
- 1,000개 작업을 제출하는 테스트는 코드상 의도이며 이번 조사에서 실행하지 않았다. “1,000명 동시 예약 보장”으로 표현하지 않는다.

## 7. 근거 상태와 유지 원칙

| 상태 | 의미 | 공개 문장에 반영하는 방법 |
| --- | --- | --- |
| 사용자 확인 | 이번 인터뷰에서 본인이 경험·의도를 확인 | 동기·담당·팀 의사결정의 근거로 사용 |
| 문서 확인 | 이력서·기존 포트폴리오의 서술 확인 | 자기기술 또는 문서에 기록된 실험으로 표현 |
| 코드·PR 확인 | 실제 파일과 변경 기록을 읽음 | 해당 구현·변경의 존재를 설명 |
| 테스트 코드 확인 | 검사 조건과 단언을 읽음 | 검사 의도를 설명, 통과·실행 성과로 확대하지 않음 |
| 미검증·미확보 | 실제 효과·운영 결과·화면 증거가 없음 | 제외하거나 가설·한계로 명시 |

사용자 확인과 코드 확인은 서로 대체하지 않는다. 기억과 남아 있는 코드가 다르면 둘의 범위를 별도로 남긴다. 모든 주장에는 아래 출처 또는 이 대화의 사용자 확인 근거를 연결한다. 저장소 원격 상태는 이후 바뀔 수 있으므로 구현에 사용할 실제 화면·파일의 출처 버전을 보존한다.

## 10. 접근성·모바일·오류 상태

- 의미 있는 제목 순서, 본문 바로가기, 키보드 포커스를 제공한다.
- 본문 대비 4.5:1 이상을 기준으로 확인한다. 색만으로 의미를 전달하지 않는다.
- 링크와 버튼 목적이 글로 이해되도록 하고 모바일 터치 영역은 약 44px 이상 확보한다.
- `prefers-reduced-motion`에서는 등장 효과와 부드러운 이동을 제거한다.
- 360px~넓은 화면에서 가로 넘침을 없앤다. 표는 모바일에서 비교 블록으로 바꾸거나 명시적인 스크롤 영역을 제공한다.
- 이미지에는 설명과 대체 텍스트, 크기 정보를 제공한다. 작은 스크린샷 텍스트에 핵심 설명을 의존하지 않는다.
- 이미지 확대는 필요한 경우만 제공하며 키보드 닫기·포커스 복귀를 지원한다.
- 이미지 로딩 실패 시에도 설명과 원본 근거 링크는 남는다.
- 이메일은 메일 앱 연결과 주소 텍스트를 함께 제공한다. 복사 기능을 추가하면 성공·실패를 알리고 수동 복사가 가능해야 한다.
- 없는 상세 경로는 설명 가능한 404와 메인 복귀를 제공한다.
- 정적 콘텐츠에 의미 없는 로딩 화면이나 빈 상태를 추가하지 않는다.

## 11. 정적 사이트의 구성과 데이터 흐름

프레임워크와 호스팅은 아직 확정하지 않았다. 구현 계획에서 정적 출력·작은 유지보수 비용·직접 경로 접근을 기준으로 결정한다. 계정·DB·관리자 화면·CMS·연락 폼·분석 도구는 첫 버전의 필수 범위가 아니다.

구성 책임:

- 공통 레이아웃: 탐색, 본문 영역, 연락·푸터.
- 메인 구성: 확정된 이야기 순서와 사례 요약.
- 상세 템플릿: 요약, 본문 목차, 판단·검증·한계, 관련 링크.
- 콘텐츠: 사례 메타 정보, 본문, 근거와 공개 상태를 소스에서 관리.
- 자산: 선별·최적화한 사진·실제 화면과 공개용 PDF.

흐름은 검토한 콘텐츠·자산 → 빌드 시 HTML 생성 → 정적 호스팅 → 방문자 열람이다. 프로젝트 상세는 각 경로에 실제 정적 결과를 만들고 새로고침·직접 접근이 가능해야 한다. 공개 페이지에서 GitHub API·Velog·개인 취업 폴더를 런타임에 조회하지 않는다.

페이지별 한국어 제목·설명, 언어 속성, 메타 이미지와 사이트맵을 제공한다. 실제 배포 주소 확정 전 임의 주소를 canonical로 넣지 않는다. 이미지 크기를 고정하고 첫 화면 외 이미지를 지연 로딩한다.

ForgeSync PDF 내 실제 화면 이미지를 추출해 활용할 수 있다. 페이지 전체를 축소해 본문으로 쓰지 않고 화면 자체를 선별한다. 과거 화면·기존 실험의 시점이 현재 정책과 다른 경우 캡션에서 구분한다.

- 조사 중 GitHub 코드·PR·테스트 읽기: 구현 존재와 검증 의도. 전체 프로젝트를 로컬 실행한 검증은 아니다.
- `output/pdf/han-seokjin-resume.pdf`: 현재 공개용 이력서. 구현에서 `/resume.pdf`로 배포할 때 파일 내용과 링크를 다시 확인한다.

## 14. 완료 확인 기준과 후속 결정

구현 완료 시 다음을 확인한다.

- 확정된 메인 흐름과 상세 5개가 있으며 모든 경로·목차·연락·PDF 링크가 작동한다.
- 한국어 중심이고 기술명·프로젝트명은 원래 표기를 사용한다.
- 회사의 비공개 자료·민감정보가 정적 출력에 포함되지 않는다.
- 현재 앱의 실제 화면·모집 링크가 없고 변경 버전의 미검증 상태가 명확하다.
- 사용자 진술, 코드·문서 근거, 실제 실행 결과를 구분한다.
- SpeakText 공동 결정과 개인 기여를 분리하고 캡처가 없는 다중 선택 UI를 증거처럼 만들지 않는다.
- ForgeSync를 불량 판별 정확도 개선·현장 검증 성과로 과장하지 않는다.
- 모플에 미확인 성능 수치·고객 업무 효과를 추가하지 않는다.
- 모바일·데스크톱 배치, 한글 줄바꿈, 키보드, 대비, 움직임 줄이기를 확인한다.
- 빌드·직접 경로 접근·404·이미지 실패를 확인한다. 성능 목표는 첫 화면 지연과 레이아웃 이동을 줄이는 것이며 측정 전 점수를 주장하지 않는다.

후속 구현 계획에서 결정할 사항은 프레임워크·호스팅, 배포 도메인, 최종 화면 자산과 상세 문안이다. 미확정 항목이 있어도 첫 버전의 콘텐츠 범위와 공개 규칙은 이 문서를 기준으로 유지한다. 공개 배포는 별도 실행 단계이며 이 문서 작성으로 게시한 것은 아니다.

현재 폴더는 Git 저장소가 아니므로 이 문서의 Git 커밋은 생성하지 않았다. 설계 문서 검토 후 구현 계획을 작성하고, 그 다음 사이트 제작으로 진행한다.
